## Threat model

What Clio protects, and from what. The rules that close it (S-xx), with their tests, are in [`security.md`](security.md); if something here changes, it changes there too.

**Starting assumption.** Any content from outside can carry instructions, and the model will sometimes follow them. Security does not depend on the model behaving: it lives in code, outside the model, and assumes the model was already fooled.

### What is protected

- Secrets and keys.
- The person's devices (nodes have a shell).
- The memory and personal data.
- Money (APIs).
- The integrity of what runs, above all what cannot be undone.
- The availability of the brain.

### From what

- Injection through outside content (the most likely).
- Compromised dependencies, extensions, skills or MCP servers.
- A stolen or lost device.
- A compromised device inside the tailnet.
- A compromised host (the PC or a VPS).
- Providers that see the data.
- The model's own mistakes, without malice.

### The worst: the lethal trifecta

Clio brings together private data (memory, files), untrusted content (web, Notion, mail) and a way out (network, messages). So the gateway decides per session, not only per action (S-05, S-06). The other known gaps and the rules that close them are in [`security.md`](security.md#gaps-in-the-design).

### The guard is at the door (ADR 0006, ADR 0012)

Clio has full use of the terminal of the machine it lives on. It is not walled into a copy; every effect goes through one door, and the door is guarded:

1. Pi and the model stay in their jail, with no credential but the model key, which reaches only the provider.
2. Every effect goes through the tool host, which decides each operation in code.
3. A judge reads outside text before the model does, withholds an injection and makes the session `suspect`; a suspect session's networked commands wait for the person.
4. Four classes of action wait for the person: delete, spend, send and control.
5. Secrets live in the vault; the model never sees a value.
6. Everything is logged, and file changes can be undone.

What this does not stop is listed under "Host mode" below.

### The agent runs as your user (ADR 0006)

There is no separate server user: the agent's tools act as you. In host mode, the factory mode, that is the point, and what limits it is the door (below). In copy mode (`--copy`, `"mode": "copy"`, `clio run --workspace DIR`) your files (`~/.ssh`, the browser profile, other projects) are kept out of reach by:

- the `clio-node` sandbox (working folder, canonical paths, symbolic links that point outside refused) and the gateway, which denies by default and does not allow free commands;
- **the `bwrap` jail** (`clio-node/src/jail.rs`) for what the agent runs: Pi's `bash` in the chat, and `run_tests` in the builtin loop of `clio run`. New namespaces (network, processes, IPC, UTS, user, cgroup), a read-only file system with only the copy visible, an empty environment, limits on processes, memory, CPU, file size and time, and a self-test in `clio doctor` that tries to escape and must fail;
- **what is shown and kept of a run**: debug mode (`--debug`, `CLIO_DEBUG=1`, `Ctrl-D`) and the context and usage views put everything through the secret scrubber (which knows the model key, in clear, base64 and URL-encoded) and through terminal sanitizing before drawing or writing; `debug.log` and `usage.json` are 0600 and without debug no `debug.log` is written (`docs/usage.md`, "Debug mode"). Only what the scrubber knows is hidden;
- the vault and the gateway are processes apart with 0600 sockets, and no Clio process listens outside loopback or `tailscale0` (`infra/local/check-host.sh` watches it);
- an encrypted disk and an active firewall on the host. If Tailscale SSH is on, whoever controls a device of your tailnet or your Tailscale account can open a terminal on the host if your ACL allows it. If you do not use it, turn it off (`tailscale set --ssh=false`).

Being in the `docker` group is the same as being an administrator. Without a tested jail (another operating system, no `bwrap` or `prlimit`, a kernel without unprivileged namespaces, a failed self-test) the copy-mode agent runs nothing: it only reads and writes inside the sandbox.

**What the copy-mode jail does NOT cover** (an honest list; see also `docs/usage.md`):

- **Kernel flaws.** It is Linux's own isolation, not a virtual machine: there is no seccomp filter, so the whole system-call surface is within reach of jailed code, and a flaw in the kernel (or in `bwrap`) would allow a way out. Keep the system up to date.
- **Side and covert channels** (timing, cache, shared processor memory): no attempt is made to close them.
- **CPU time and host resources.** A cap of 120 s of wall clock, 120 s of CPU, 2 GiB of virtual memory and 128 processes bounds the damage, it does not remove it: a command can use several cores for that time. There are no disk quotas: a program can fill the copy with files (each up to 64 MB) or `/tmp` up to 256 MB (the `/tmp` cap needs `bwrap` 0.9 or newer; 0.8 has none). Virtual memory (`RLIMIT_AS`) is not real memory.
- **What is inside the copy.** Jailed code can read all of it and change it. What you do not want read must not be in the copy (the copy already leaves out what looks like a secret). What changes still goes through your `diff` and your `apply`, which refuses protected paths and symbolic links.
- **What it prints.** The output is outside content: it is cleaned, wrapped as data, marks the session and, with the judge on, is judged before the model reads it; a weak model can still be swayed by it; the defense is the gateway, not the prompt.
- **`/usr` is readable** (program versions, which packages are installed) and `/proc` shows data about the machine (CPU, memory, kernel).
- **The model adapter and `clio` itself** are not in the jail: they run as your user. In the `run` path (the builtin loop) only `run_tests` is jailed; in the chat, Pi itself runs jailed (ADR 0009, next section).
- **A `kill -9` of `clio` during `doctor`** can leave a harmless decoy file in your HOME.
- **`cargo test`** is not offered: it would need part of your HOME mounted.
- **The bench (`clio-bench`)** runs each task's `check` on what the model wrote: that `check` runs in this same jail (no network, no HOME, no environment). Without a jail it does not run, unless `CLIO_BENCH_CHECK_JAIL=off`.

### The Pi stack: Pi + `clio-guard` + `clio-toolhost` (ADR 0007)

Pi runs the agent loop, the providers and the sessions; Clio does not rebuild its tools, it only changes where each primitive operation runs. Pi 1.4.0 starts with `--no-builtin-tools --no-extensions -e clio-guard --no-mcp --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve --offline`. The extension registers Pi's tools (`read`, `write`, `edit`, `bash`, `find`, `ls`; not `grep`, because it always starts `ripgrep` on the machine) with operations of its own that travel to the service, Clio's thirteen memory tools (four read; `memory_save` and the others write at once, because the memory is the agent's; ADR 0010), `ask_person`, `request_secret` and `todo_write`, and in host mode `job_output`, `job_stop`, `service_write` and `service_status` (S-69), and `mcp_propose`, `mcp_tools` and `mcp_call` (S-70). Pi itself says it is not a security boundary: security comes from isolating what it can reach. Layer by layer:

| Layer | What it defends | What it does NOT defend |
|---|---|---|
| Pi's start flags | No built-in tools, no foreign extensions, no MCP, no skills, no context files; an extension that does not load stops Pi (without it there are no tools left). | It is not a boundary: it runs inside Pi's process. |
| The `clio-guard` extension (`adapters/pi/extensions/clio-guard/`) | Registers only its tools (22, or 24 in host mode), blocks and reports any other and, in copy mode, writes outside the copy or into protected folders; always refuses `project_trust`; sends the person's `bash` through the same path; adds the versioned prompt (fails closed if it is missing); marks every tool result as data and passes it through the service's filter; keeps the taint in Pi's session and restores it on reopening. | **It runs inside Pi's process, in Pi's jail.** A flaw in Pi or in one of its dependencies voids this layer; that is why it decides nothing the service does not decide too. |
| The `clio-toolhost` service | The only thing that runs effects. A 0600 Unix socket in a 0700 folder; the gateway decides each normalized operation (deny by default, fail closed, circuit breaker after 10 denials in a row). In copy mode the `clio-node` executor works in the copy (canonical paths, links that point outside refused, `extensions`, `skills`, `.pi`, `.claude`, `.git`, `.agents`, `.vscode`, `.husky`, `.githooks`, `.cargo` and `.devcontainer` not writable); in host mode it works on the machine through the host launcher (next section). Every read and command output is sanitized and passed through the vault's scrubber, and the final filter cleans and wraps whatever Pi made of it; with the judge on, outside text is judged there before the model reads it. The taint is never cleared and goes with every answer. It serves the memory tools (S-60, S-61, S-65). If it falls or stays silent, the tool fails and nothing runs. | It shares a user with Pi's jail: whoever controls Pi can talk to its socket and do what the model can, with the same gateway in front. A gateway "ask" is a no: nobody answers it. (The set-aside classes of host mode are a separate step, after the gateway allows the call.) File names come out of a listing as they are (Pi has to be able to ask about each one) and are cleaned in the final filter. |
| The copy-mode `bwrap` jail | **`bash` always runs here in copy mode** (S-12): no network, `HOME` hidden, only the copy visible and writable, `.pi`, `extensions`, `skills`, `.claude`, `.git`, `.agents`, `.vscode`, `.husky`, `.githooks`, `.cargo` and `.devcontainer` read-only (the ones that do not exist are created empty for the command so they cannot be created from inside, and removed afterwards), limits on time, processes, memory, file size and output. It is offered only if the self-test passes; otherwise `bash` fails closed. The service's `S-12/bash` rule adds the minimum on the command's text: not empty, no NUL, up to 8 KiB. | What the previous section says (no seccomp, no disk quotas). What the command does inside the copy is legitimate: it can read, change and delete it; what changes still goes through the person's review. |
| The judge at the door | Outside text a tool brought in is judged before the model reads it (one closed question, `injection`, on text the vault cleaned; at 0.9 or more it is withheld and the session becomes `suspect`). | It is optional and probabilistic: off, down or silent (past 5 s), the text arrives as before, wrapped as data. The judge reads all of a text, in 24 KiB windows that overlap by 2 KiB asked at once; beyond 16 windows it counts as unjudged. |
| Vault / scrubber | Known values and key patterns are struck out of every read, command output and final result, even when split with invisible characters (it sanitizes before cleaning). | Only what it knows. If a vault is configured and does not answer, the output is withheld. The bytes `edit` reads to rewrite a file are not cleaned (that would damage the file); its result is. |

**Honest limits of this stack:**

- **Pi's process and the extension run as the person, but inside a `bwrap` jail** (ADR 0009): they do not see the vault or your files, the working copy is read-only to them (every change goes through the tool service), and their network is their own: they reach only the model provider's address, through a host proxy that refuses everything else, and not the host's loopback or abstract sockets. What is left: Pi keeps the provider's key and can send what it read to that one address (which already gets the model's whole context). If the jail or the proxy do not start, or the self-test fails, Pi does not start. What the jail refuses is shown in the chat.
- **The `S-12/bash` rule does not read the command**: what a command can do is bounded by the jail or the launcher, not by a word list. An `S-12/bash` denial does not count toward the circuit breaker (it does not go through the gateway's count).
- **The taint alone closes no way out.** In copy mode no tool has a network, so S-06 is not exercised; the mark exists, persists and is reported. In host mode a command can ask for the network: a session that is only marked still runs it (what is set aside is set aside with or without the mark), and a session the judge made `suspect` has every networked command set aside as send.
- **The taint notice in the system prompt** is built when each run starts, not between turns of one run; inside a run what protects is the data wrapper on every result.
- **Once the circuit breaker is open** (10 denials in a row) the session runs nothing more by itself: the person has to decide, and today the remedy is to start another session.
- **What the memory tools read leaves the machine** (S-60, ADR 0010):
  - The model's provider sees what the tool returns, as it already sees the context (S-44). The budget (20 calls, 24 KiB, per session in a rolling hour) limits how much can leave, not whether: what must not leave the machine must not be in the memory.
  - They share a user with Pi: a compromised Pi can talk to the service's socket and make the calls the model can, with the same gateway and the same budget in front. It cannot open `memory.db`: the jail does not see it.
  - An **active** memory of origin `agente` can carry an old injection (a clean run that wrote it without knowing). That is why it arrives wrapped as data and marks the session; the defense is not a text filter.
  - There is no sensitivity class: everything active can be read. Quarantine (what was forgotten), what is archived and another scope's cannot be read, and the errors do not say which of the four cases it is.
  - Opening the memory read-only leaves no usage signals: the statistics do not show what the agent read by tool.
  - The agent writes its memory at once (`memory_save`, `memory_update`, `memory_forget`, `memory_pin`, `memory_consolidate`, `memory_revert` of its own; see "Memory as an attack surface"); there is no tool or operation that promotes, archives or purges (asking for one is an undeclared operation, S-02). The only one that writes as the person is `memory_block_edit` (their blocks: identity, rules, preferences, watch list): at once only in a session that read nothing from outside; in a marked one the exact change is set aside and written only when the person approves it (the model has no tool that approves).
- The start check of the tools relies on what the extension reports (`pi.getActiveTools()` / `pi.getAllTools()` with their source) and on the tool list the model receives; Pi's RPC has no command that lists them.
- The link between the extension and the service is not authenticated beyond the socket's permissions (0700 folder, 0600 socket, same user).
- **Pi writes its session files** (it has read-write access to the sessions folder), and `clio` reopens the newest one with no key pressed. Clio seals a session's file (size and SHA-256, in the run folder Pi cannot write) when it opens and after Pi has stopped at close; a reopened file that does not match, or one of a run with no seal that changed after Clio started sealing, marks the session (a forged "person" turn arrives in a marked session) and the chat says so. A file Pi backdates to before the first seal of a run from before the seals is not caught. The history reader caps what it reads from that file (128 MiB, 512 KiB per line, 5,000 entries per page).
- **One `clio` per conversation**: opening one holds an advisory lock in its run folder, so two terminals never run two Pi on one file and two tool hosts on one run folder.
- `grep` stays out while Pi does not allow confining its search; `bash grep` replaces it.

**Done (ADR 0009):** Pi runs inside `bwrap` with the minimal file system (phase 3a) and its own network with the provider as the only destination (phase 3b).

### Host mode: the tools on the real machine (ADR 0012)

In host mode (`"mode": "host"`, `clio --host`, and the factory mode since 2026-11-18, by the owner's decision: an agent that only sees a copy cannot manage the server it lives on) there is no copy: the tools act on the person's machine, with the network when a command asks for it and with `sudo` where `sudo` needs no password. Copy mode (`"mode": "copy"`, `--copy`, `clio run --workspace DIR`) does not change. What is no longer contained, and what still is:

**What is no longer contained:**

- **Your files and your services.** The tools read and write in `/` with your permissions, and a command runs in your home folder with the whole system in view. There is no `diff` and no `apply`: what changes, changes now.
- **The network.** A command with `network: true` goes wherever it wants. It marks the session, and only a `suspect` session sets it aside.
- **`sudo`.** With the `systemd` launcher (`sudo -n systemd-run`, where `sudo` needs no password) a command can become root, and then nothing below stops it: neither Clio's masked folders nor the list.
- **The list of what is set aside is a list, not a wall.** A script, a variable or an alias gets around it. Against that there is the action log and the prompt's rule.
- **What a command changes has no copy and no undo.** Only `write`/`edit` (and `fs_mkdir`) keep a copy before changing and are undone exactly with `clio undo`.
- **With the `systemd` launcher, even without `sudo`, a command reaches Clio's files through `/proc/<Clio's pid>/root/…`** (same user; systemd 255 has no process namespace of its own for the unit). Checked by hand on the VPS on 2026-11-17. With `bwrap` that path does not exist (the command has its own process namespace), but that does not make the masks a wall: the next point remains.
- **Daemons outside, through their Unix sockets, with both launchers.** A command sees `/var/run/docker.sock` and the user's bus (`/run/user/<uid>/bus`): `--unshare-net` and `PrivateNetwork` cut the network, not Unix sockets. With Docker (being in the `docker` group is being root) a command without `network: true` reaches the internet and mounts Clio's data in a volume; over D-Bus it asks the person's systemd to run something outside the launcher, unmasked (`systemd-run --user …`, also `clio approve <id>`). They are not masked, because managing Docker and the services is legitimate work: `systemd-run`, `gdbus`, `dbus-send` and `busctl` are set aside (`control`), and `docker`, `docker-compose`, `podman`, `ssh`, `scp` and `rsync` mark the session even when they do not ask for the network.
- **A command with no time limit runs until it ends or is stopped.** The model gives `timeout` when it expects the command to end by then (capped at 3600 s); without it there is no limit. Esc, an abort, quitting or the end of the session stops it, under both launchers, and the log says `stopped`.
- **Background jobs** (`bash` with `background: true`) keep running between turns: at most 4 per session, all stopped when the session ends. Their output is outside data like a command's, and judged when the job reached out.

**What is still contained:**

- **Pi stays in its jail** (ADR 0009): in host mode its working folder is an empty folder; it sees neither your files, nor the vault, nor the network except the provider. Only the tool service acts.
- **Clio's folders** (configuration, data, runtime, the memory): the file tools refuse them by direct path, by link and by `..` (`host/control`), a command that names them is set aside (`control`), and a command sees them empty and read-only (except as said above).
- **Fail closed.** Without a launcher that passes its self-test (Clio's folders masked, network cut without `network`) there is no `exec`; it never runs unmasked.
- **Four classes are set aside** (delete, spend, send, control): they do not run until the person says yes (`clio approve`, or the question at the end of the turn), they run once and exactly as saved (same hash), and they expire after 24 hours. At most 3 questions a day; the rest go to the day's summary.
- **The judge at the door.** With Jev on, what a tool brought in from outside (a foreign folder, a networked command, a program that reaches out, logs) is judged before the model reads it. An injection is withheld: the model gets only its size and source, the text is kept for the person (`runs/<id>/toolhost/withheld/`, 0600), the session becomes `suspect`: its background jobs with the network are stopped, and from then on every command that asks for the network, reaches out by itself (such as `ssh`, `docker`, `crontab` or `nsenter`) or names `sudo` is set aside as send, with the reason shown. Off, down or silent: as before.
- **Secrets.** The model sees names, never values. When a task needs one, `request_secret` leaves a request of class `secret`; the person types the value into the chat's masked box (or `clio approve <id>` at a terminal) and it goes to the vault's person socket from Clio's own process, never through Pi, the guard, the tool host, the model, a log or the pending file. Today no tool of the model sends a stored secret anywhere.
- **Everything is logged** (`actions.jsonl`, 0600): a line before and after every command and write, with known keys struck out; without the line before, it does not run. Background jobs log `start`, then `done` or `stopped`; what the judge withheld gets its own line.
- **The mark.** Reading a foreign folder (`/var/log`, `/var/mail`, `/var/spool`, `uploads`, `Downloads`, `Descargas` and those `host.json` adds), a command with the network or one that reads logs (`journalctl`, `docker logs`…) marks the session; a marked session does not change the person's blocks by itself (`memory_block_edit` is set aside for the person's approval). The output still arrives cleaned and wrapped as data. Case 62 of the battery.
- **A budget per day** (cost and steps, across sessions), on top of the cost cap per message and the anti-loop.

**Limits worth knowing:** two host sessions at once can undercount the day's budget (each keeps its own count and the last one wins); what is approved runs in another process (a new tool service on that session's folder), not in the session's own; an `rm -r` under `/tmp/` is not set aside (the written path is what is checked); tool calls the model issues in the same step as a read run before the judge's verdict marks the session, so the suspect mark only stops what comes after; a skill's script is classified by its command line, not by what it does inside (S-68: the review checks that); a service's limits are per process when no user scope can be made (S-69). **Host mode's own commands are not contained against Clio:** the chat's commands run under the systemd launcher as the person, with `sudo`, so a fooled model can reach Clio's data, the pending store and the vault's sockets, through `sudo`, or without it through `/proc/<pid>/root` of the person's other processes (no private pid namespace before systemd 257). What stands between a fooled model and that is the judge and the set-aside list (`control`), not containment. This round does not change it; a review's and a service's commands run under bwrap, which hides them.

### The reviewer: a second jailed agent (S-67)

A review (`/review`, or the judge's after a turn that changed something) starts a second Pi that checks a piece of work and tries to break it. It is built so it adds no way in and no way out that the session did not already have:

- **Started like the session's Pi**: the same jail, connector, launcher rules and guard, its own session, run folder (`runs/<id>/reviews/<n>/`) and tool host (`clio toolhost --review`). Its own tool host, not the session's: the tool host runs one call at a time (the review and the chat would wait for each other), and it keeps the mark in its run folder (a shared one would mark the conversation from the reviewer's reads, whatever it found).
- **Clean context and fixed tools**: its prompt (`clio-reviewer@3`) and the review request, the subject inside the data markers; never the conversation, the person's blocks or the memory. Four tools: `read`, `bash`, `find`, `ls`, under the session's mode rules (its `bash` in a copy runs in the copy's jail, on the real machine in host mode, with the same list of what is set aside).
- **Nobody to ask**: what would wait for the person is refused at once and nothing is left pending; no `ask_person`, no `request_secret`, no memory, no background commands.
- **The same marks and budget**: it starts marked if the session is (a `suspect` session's reviewer asks before what a `suspect` session asks, so it is refused), spends from the same day's budget, and stops at its own time and step caps. What it runs is in the action log under its own run (`<id>.review-<n>`), and `/actions` shows it with the session's. Its own cost cap is `review.max_cost_micro_usd`.
- **What comes back**: only a fixed block, read strictly; anything else is `could not check`, shown to the person as data and sent nowhere. Findings go to the session's model as data (`subagent-summary`) with Clio's request to fix what is right and say what it does not accept, after the judge read them like any outside text; a reviewer that read something from outside ended marked, and its findings mark the session the same way (if that mark cannot be made, they are not delivered).
- **No network, no `sudo`, no writes to the copy**: its tool host serves only the reading tools and `exec`; a command that asks for the network, reaches out by itself or names `sudo` is refused outright (a review cannot check what needs them); in copy mode the copy is read-only to its `bash`, in host mode the machine is read-only but `/tmp`, with no new privileges.

**What it does not defend:** it is not an injection guard. It is another model of the same family reading the same text: what fooled the author can fool it, and a hostile subject can steer its verdict. A `passes` proves nothing to the guards: the tool host, the list, the judge and the marks apply to the next turn exactly as before. Its findings can carry text the reviewer read from outside; they arrive as data and mark the session, as any other outside text. In host mode its `bash` runs as the person on the real machine: what it can still write is `/tmp` (shared with the person's other programs), and what any user can reach without writing a file (a local socket or service it can talk to, such as a user D-Bus or a database on a Unix socket); `sudo` is refused by its name and, with the `Systemd` launcher, has no new privileges to gain. The `sudo` check is a word match: a command that hides the word is caught only by the launcher (`NoNewPrivileges` with `Systemd`, `no_new_privs` with `Bwrap`). In copy mode its `/tmp` lives for one command only. Read-only means a check that must build or write next to the code cannot run there: it is `could not check`.

### Skills: instructions that persist (S-68)

A skill is text the model follows in every later session, plus scripts it runs: the same kind of risk as a persistent memory, with commands attached. So the way in is narrow and the way out is the same as any command:

- **One writer.** The skills folder (`~/.local/share/clio/skills/`) is written only by the person's own `clio` process. Pi sees `live/` read-only in its jail; the tool host refuses Clio's folders to every file tool; host-mode commands get a read-only `live/` and a command that names any other part of the folder is `control`. The model's only way is `skill_write`, which stores a draft and registers nothing.
- **Four gates before it counts.** The tool host's checks (name, sizes, paths inside the skill, no characters the display would change, no secret shapes, a check to run that is not just `true`, `:`, `exit 0` or an `echo`); the judge reads the whole text (an injection is refused and makes the session `suspect`); the reviewer (S-67) gets every file whole in its request and runs the check in a staged copy that lives in Clio's data folder (`<run>/reviews/<n>/stage/`, made new level by level, never through a link; no jail sees it, and in host mode only the reviewer's commands, read-only), and the copy is compared with the draft after the review (changed: `could not check`); and registration, at once only for a `passes` in a clean session (findings under `passes` are notes for the model, once an hour per name, not a blocker: the reviewer's prompt keeps `fails` for a failed check, a skill that does not do what it says, or one unsafe to run unattended). A marked session (the draft keeps the marks the session had when it was written), a review that could not check, a change to the shipped `skill-creator` or a name the person removed waits for the person, who sees every file whole (scripts too) and confirms it at `clio approve`; approval registers exactly the bytes shown (bound by hash). Six drafts an hour per session (taken ones count), and a name dropped after three failed reviews is refused for an hour.
- **Undo and off.** Every version is kept; the person can turn a skill off, go back a version, or remove it (asked first). Three failed `skill_report`s turn it off by themselves.
- **Its scripts are commands.** A skill's script runs through the tool host as a command: its command line is classified as the same line typed (the same classes set aside), the same judge on its output, the same log, and it sees the skill read-only and nothing else of Clio's. In copy mode the command jail does not see the skills, so scripts run only in host mode.
- **When Pi sees it.** A registered skill reaches Pi at its next start (a new session, or reopening one): Pi's RPC has no reload, and the guard's in-process reload was not used, since it reloads the guard itself in the middle of a session.

**What it does not defend:** a skill that passed is trusted text: its file reads unwrapped and does not mark. The set-aside classes see a command line, not what a script does inside: `bash <skill>/scripts/x.sh` is classified by that line, so a deletion inside the script is not set aside. What a registered script does is checked by the review (and by the person, when it waited for approval), not by the classes. The judge and the reviewer are models; a skill written in a clean session from a request that was itself a well-disguised attack can pass both. What limits the damage is that the skill can only make the model do what the model could already do, under the same rules, and that the person is told of every registration and can undo it.

### Services: programs that run with nobody watching (S-69)

A service is a program the model wrote that keeps running on the person's machine, on a schedule, with no model and nobody looking: a persistence mechanism by design, so its whole shape is approved by the person and enforced at every run.

- **One writer, one approver.** The services folder (`~/.local/share/clio/services/`) is written only by the person's own `clio`: it is inside Clio's data, which the tool host refuses and every jail masks. The model has `service_write` (a draft, host mode only) and `service_status` (read, outside data that marks); no tool approves, runs, turns on or off, removes or edits one, `clio services …` and the `clio-services` timer units are `control`, and so is a write under `~/.config/systemd/` or `~/.local/share/systemd/`. Every new service and every new version waits for the person after the judge and the reviewer: the box shows everything it is granted and every file whole, and approval is bound by hash.
- **What runs is what was approved.** Before each run the version folder is read back without following links and must hash to the approved version (no extra file either); otherwise nothing runs, it is paused and the person told.
- **The run's bounds.** bwrap only (the systemd launcher cannot hide other processes' `/proc/<pid>/root` without a private pid namespace, which systemd gives from 257: a run under it is refused, saying why), as the person, `NoNewPrivileges`; the machine read-only but its own state folder and the paths it declared (checked when written, approved and run: under the home, existing, never Clio's folders, keys, shell start files, autostart or code-loading folders, no dot name, no repository in its tree); **nothing of the home visible**, nor of `/home`, `/root`, `/var`, `/srv`, `/opt`, `/mnt` or `/media` (a web root's secrets, a database's files), but its own folder and the paths it declared to read (under those) or write (under the home): a read-only home still lets a program connect to a socket in it (a process manager's, a terminal multiplexer's: a way to run something outside the jail) and read every credential, so the whole home is hidden; a private `/tmp` and `/dev/shm` the size of its memory; Clio's folders (the vault's sockets and file, the pending store, other services' state) and `/run` (the person's D-Bus, Docker's socket) hidden; its own pid namespace and `/proc`; no network of its own, its declared hosts only through an allow-list proxy that connects only to public addresses it checked (a name that points at the machine, its network or the cloud's metadata service, then or after approval, reaches nothing); its time, CPU, memory and process limits.
- **Secrets.** Released by the vault to the runner only when it lets the secret go to every declared host (`service:<host>`; the run could send it to any of them), handed to the run on its standard input into one variable; scrubbed (by value and by the vault) from everything it prints before anything is kept. A locked vault means the run waits.
- **No silent failure, no runaway.** Every run is recorded; three failures pause it; `attention` (exit 10) tells the person when a chat opens; one run at a time per service; one catch-up run after a gap.

**What it does not defend:** inside its bounds a service does what its code says, every time, with nobody watching: the review and the person's reading of the box are the check of what that is. A declared write path or host is the service's to use as it likes. Its limits hold for the whole run only when the person's systemd user manager can make a transient scope (`MemoryMax`, `MemorySwapMax=0`, `CPUQuota`, `TasksMax`); otherwise they fall back by themselves to per-process limits (`prlimit --as`, `--cpu`, `--nproc`, `nice 19`): a service can then start up to 256 processes, each under the limit, address space is not resident memory, and CPU is a budget of seconds per process, not a share. Each run records which applied. The timer runs as the person's user manager: with lingering off it stops when the person logs out (Clio says so and prints the command; it does not run it). A host-mode command could still create a differently named user timer that calls `clio services run-due`: that runs only services the person approved, on their schedules. A secret given to a service can be sent by it to its declared host (that is what it is for) and printed in a transformed form the scrubbers do not recognise.

### MCP servers: someone else's code with the person's credentials (S-70)

**Plainly: an MCP server the person approved is a third party's program running on their machine. It holds the credentials the person gave it, and it can send them, and anything it is handed, to the hosts the person allowed.** Clio decides what reaches it and what it reaches; it cannot decide what its code does inside those bounds.

- **One writer, one approver.** `~/.local/share/clio/mcp/` is Clio's data (refused and masked). The model has `mcp_propose` (a proposal, host mode only), `mcp_tools` and `mcp_call`; nothing it can call downloads, installs, turns on, confirms, removes or sets a tool's mode, and `clio mcp …` is `control`. Every proposal waits for the person as class `mcp`, bound by hash, with npm's facts, the hosts, the secrets and every host each can reach, the paths and the limits.
- **Nothing runs before approval.** Before approval only `npm view` runs (in a jail whose only host is the registry): the package's name and version leave the machine, nothing is downloaded. The proposal's fields are checked so none can become an npm option, a URL, a git source, a path, a tag or a range: npm installs exactly `package@version`.
- **The probe.** After the install the server starts once from the staged tree with no network, no secrets, no reads and no writes, and an empty temporary home (an update's data is kept only once it is confirmed), and is only asked for its tools; it stays off until the person confirms them in a box that lists every tool whole, with what each runs as in plain words, bound by a digest of that list. A server that phones home or reads a key on start finds neither. A failed install tells the model only the step that failed, in fixed words; what npm or the server printed goes, cleaned, to the server's log (`/mcp logs`).
- **No flood, no swap.** At most six proposals an hour per session, counted before npm runs; one npm at a time; none from a `suspect` session. A name belongs to one package: another package under it is refused, and an identical proposal is refused.
- **The run's bounds** are a service's (S-69): bwrap, as the person, `no_new_privs`, its own pid namespace; `/home`, `/root`, `/var`, `/srv`, `/opt`, `/mnt` and `/media` hidden (a web root, a database's files, another user's home) but its own data folder and the paths it declared; its installed tree, the Node binary and npm's own folder read-only, and nothing more of them (a Node whose window would show the home or Clio's folders is refused); Clio's folders (the vault's sockets, the pending store, other servers' data) and `/run` hidden; the network only to its declared hosts through the allow-list proxy, which reaches no private or local address; its limits (a scope's, or per process). Its secrets are released by the vault only when they may go to every declared host (`mcp:<host>`), handed over on standard input.
- **What changes is caught.** Before each start the installed tree must hash to what was installed (else it is turned off and not started); a running server that was turned off, removed, updated or never confirmed is stopped before the next call and by the idle reaper. A tool whose description or schema differs from what the person confirmed, or a new tool, is `ask` and flagged until the person confirms again: descriptions are prompts (S-15).
- **What the model gets** is outside text: every tool list and result is scrubbed, judged and marks the session; a `suspect` session sets every call aside. Arguments are checked against the tool's schema and must not look like a secret. An `ask` tool runs only as the person saw it.
- **The client** is Clio's own, in Rust: it reads lines of at most 2 MiB and a bounded number of messages, has a time limit on every call, refuses every request the server makes (no sampling, roots or elicitation), and stops a server that floods, hangs or crashes without stopping the tool host; a slow server holds only its own calls, never another server's or the close.

**What it does not defend:**

- **The package's own code runs.** "An exact version, a lockfile with integrity hashes and no install scripts" pins *what* is installed and stops code running at install time; it says nothing about whether that code is honest. A malicious or hijacked release (a stolen maintainer token, a typo-squatted name the model picked, a dependency that turned bad before that version was published) runs at its first start, inside the jail. Install scripts are skipped, so a package that needs them may not work; a package that downloads more code at run time can do so only from its declared hosts. The integrity is npm's own, from the registry the person also trusts for the name: Clio does not check signatures or provenance.
- **Inside its bounds it does as it likes.** It can send its secrets and whatever it is given to any declared host, write anything in its declared paths and its data folder, read its declared `reads`, and lie in its results (which is why they are outside text). A `free` tool is one the person chose to let run without asking: a server that claims a tool only reads may be wrong.
- **The probe proves little.** A server can behave during the probe and differently later (with network, with secrets, on a date). The probe only keeps secrets and network out of the first start and gets the tool list.
- **Limits** are a service's, with the same per-process fallback; a long-lived server's CPU budget per process is an hour.
- **The registry learns** which package and version Clio looked at, from this machine, before the person approves.

### Memory as an attack surface (injections that persist)

A normal injection dies with the run: the hostile content only lives in that session's context. Memory across runs changes that: if a text from a file, a web page or a test output manages to be saved as a "memory", it comes back into the context of every future run, without the warning that it came from outside. It is an injection that persists, and also a way to poison what Clio believes about you (for example "the person authorized X"). What bounds it (`crates/clio-brain/src/memory_link.rs`):

- **Who writes** (S-25, S-27). The memory is the agent's (spec `2026-11-04-clio-memory-standalone-design.md`): in the loop of `clio run` what was learned is written once at the close; in the Pi stack the agent saves, corrects, forgets, pins, merges and undoes its own with its tools, all active at once, with actors of their own and an hourly quota each (500 for the agent, a brake on a loop). None of that promotes, archives or purges (S-60).
- **The origin `persona` is written only by the person** with `clio memory remember`. What the agent saves after reading something from outside, and what the model asks to remember when closing a run, goes in as `externo`; the agent actor cannot even declare the person's origin (the library downgrades it).
- **Origin in view, not quarantine** (S-25, S-27): nothing the agent writes waits for review; what came after reading something from outside stays active marked `externo`, reading it taints the session, the loop of `clio run` does not see it (unless the person has it in a block), and a fixed block does not follow an `externo` correction. Quarantine is only what was forgotten (`memory_forget`, the originals of a merge): it does not come out in `recall` or in the context, and it keeps its record. Every change goes into the operations log and the person reverts it.
- **Procedures** (S-26): the "how it is done" memories go in active like any memory, with their origin; the ones the model asks for when closing a run are always `externo`.
- **What is recalled comes back as data**: in a layer of its own, `memoria`, wrapped as untrusted content, with each memory's id, after the secret scrubber and the filter of what goes to the model (S-18, S-44).
- **Reading by tool** (S-60, ADR 0010): the tool service answers the read tools and opens the memory read-only. Only active memories come out; the memory is global (every project, each memory marked with its place), and those in quarantine, archived ones and those outside Clio's memory get the same error as one that does not exist. What comes out is cleaned, one line per memory, wrapped as data with the source `memory`, and marks the session as tainted only if a memory is not the person's (origin `agente` or `externo`). Each session has a hard cap of 20 calls and 24 KiB of returned text in a rolling hour (`S-47/memory`) and a log of facts (ids, counts, a short hash of the query; never text). An order written inside the copy is carried out even if it comes from a memory: the defense is that it arrives as data, the session is marked and the person reviews the copy with `diff` and `apply`; only the ones that point outside the folder or into a protected one are refused (S-13, S-16). Cases 56 to 60 of the battery.
- **Writing by tool** (S-61, S-64, S-65, S-27): `memory_save` and the others have no arguments for the actor, the origin or the scope: the service sets them (actor `agente`, origin `agente` or `externo` depending on the session, the session's places), so an order inside a file cannot get a memory with the person's origin. The text goes first through the vault's scrubber and, if it had a secret, is not saved; the engine applies its detector and the hourly quota of the actor `agente`. With Jev on, Jev asks before writing whether the text is unsafe or not worth keeping (a clear "no" saves nothing). Each session can save five an hour if it read something hostile, thirty if not, and make ten changes an hour (`S-47/memory`; a rolling hour by the tool host's clock, never reset by a compaction; they count even when they fail and survive a restart of the service). The agent's `memory_revert` only undoes what the agent signed. The memory is opened for writing only during the call. What is left: a fooled model can save harmful text (active, marked `externo`) or forget or correct good memories; the defense is the marked origin, Jev when it is there, the operations log and `clio memory revert`. Case 61 of the battery.
- **Clean text**: control characters are replaced when saving, and sanitized again when shown (TUI, CLI), even if another tool wrote the file.
- **Secrets**: the scrubber strikes out what it knows (and key patterns) and the library's detector refuses the rest before writing; a refusal is noted in one line and does not break the run's close.

What it does **not** bound: the request you write is kept as part of the run's record (active in a clean run); if you paste text from a hostile web page into it, that text stays as an active memory and comes back in future runs, marked as data but without quarantine. What the agent saved after reading something hostile is active: the defense is its `externo` mark (and Jev), not your review; if you see it, `clio memory revert` undoes it. An active memory of origin `agente` (from a clean run) can carry an injection nobody saw; reading by tool delivers it wrapped and marks the session, but does not detect it. Archiving does not delete (until PURGE arrives, the text stays in the file and in the log, unencrypted). The secret detector does not see what does not look like a key (personal data without a key shape is saved if you write it).

### Out of scope

An attacker with control of the person's device and of their passkey: there the signature no longer tells the person from the attacker. The spending caps and revoking the brain in Tailscale limit it.
