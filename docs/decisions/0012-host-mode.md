# 0012: Host mode, the tools on the real machine under a few fixed rules

Status: accepted (2026-11-17). Built on the branch `feat/manos-reales` (plan `docs/superpowers/plans/2026-11-17-manos-reales.md`; design `docs/specs/2026-11-17-clio-asistente-autonomo-design.md`, section 2). Copy mode stayed the factory one until 2026-11-18 (see "Factory mode" below). Extended on 2026-11-18 on the branch `feat/guard-at-the-door`: time limits chosen by the model and stopping, the judge at the door and the `suspect` mark, background commands, `request_secret` and its `secret` class, and the prompt `clio-host@5` (sections from "Time limits and stopping" on). [ADR 0006](0006-local-first-vps-optional.md) records why this is the security model now: the guard is at the door.

## Context

Until now the agent worked on a copy of one project: `bash` ran in a `bwrap` jail with no network and only the copy visible, and the person brought changes back with `diff` and `apply`. The design of Clio as an autonomous assistant asks for the opposite: the agent acts on the person's machine, with the network and with `sudo`, and the person approves only a few kinds of action, without the task stopping to wait. Two facts shaped how:

- **`sudo` does not run inside `bwrap`.** `bwrap` sets `no_new_privs`, so `sudo` refuses (checked on the VPS on 2026-11-17). A jail that hides Clio's folders and a free `sudo` cannot both come from `bwrap`.
- **A list of program names cannot decide what reaches the network** (`curl`, `wget`, …): any script gets around it without meaning to.

## Decision

**Pi stays in its jail** (ADR 0009). In host mode its working folder is the person's home path, but inside its jail that path is an empty folder: nothing of the person is mounted. The guard (`CLIO_GUARD_HOST=1`) sends absolute paths and lets the service decide. Only the toolhost's tools reach the real machine (`Config.host`): the file tools work on `/`, a relative path is taken from the home folder, and `exec` runs through a host launcher of `clio-node` (`crates/clio-node/src/host.rs`).

**Clio's own folders** (`Dirs.config`, `Dirs.data`, `Dirs.runtime`, and clio-memory's data folder when it lives elsewhere) are refused by the file tools wherever the path really lands (canonical, through links and `..`; rule `host/control`), and a command sees them empty and read-only.

**Two launchers**, chosen by `HostJail::detect`:

- **`Systemd`**, when `sudo -n true` works and `systemd-run` exists: `sudo -n systemd-run --wait --pipe --collect` starts a transient system unit that drops to the person's uid and gid, in the home folder, with `TemporaryFileSystem=<folder>:ro` over each of Clio's folders, `PrivateNetwork=yes` unless asked, `KillMode=control-group`, `RuntimeMaxSec` as a backstop when the command has a time limit (none when it has none), and an environment emptied down to `HOME`, `USER`, `LOGNAME`, `LANG`, `PATH` and `XDG_RUNTIME_DIR`. Inside, `sudo` works. On timeout, or when the command is stopped, the client is killed and the unit stopped with `sudo -n systemctl stop`. A folder whose path systemd would split (spaces, colons, quotes) is refused, not passed unmasked.
- **`Bwrap`** otherwise: `bwrap --bind / /` with a read-only `tmpfs` over each of Clio's folders, `--unshare-net` unless asked, `--clearenv` and the same environment, and its own pid namespace (`--unshare-pid`, `--die-with-parent`): when the command ends or is killed, everything it started dies with it. No `sudo` here, and none needed.

Both **fail closed**: at start the launcher runs a self-test (a decoy in a masked folder is not visible, the mask cannot be written, the network is cut unless asked for and reachable when asked, and with `Systemd` `sudo -n true` works inside). If it does not pass, host mode has no `exec`; it never falls back to running unmasked. `clio doctor` shows the launcher and its self-test, and warns that Clio's console will have no `sudo` when it is `Bwrap`.

**The network is asked for per command** (`network: true`). A command without it has none. A command with it **marks the session** (source `web`), so the mark comes from the core, not from a list of program names. The cost: checking `localhost` also needs the network, and marks.

**What marks a session in host mode:** reading (`fs_read`, `fs_list`, `fs_glob`) under a foreign folder (factory: `/var/log`, `/var/mail`, `/var/spool`, and any folder named `uploads`, `Downloads` or `Descargas`; the person adds more in `host.json`); a command with `network: true`; a command whose program reaches past the network cut by itself (`docker`, `docker-compose`, `podman`, `ssh`, `scp`, `rsync`); a command that names a foreign folder or reads logs (`journalctl`, `docker logs`, `docker compose logs`, `kubectl logs`); and, as in copy mode, memory of the agent's or outside origin, and a mark restored from the run folder. Reading the person's own files does not mark. Output is still scrubbed and wrapped as data. A marked session's `memory_block_edit` is set aside for the person (class `memory`, below) instead of written (S-60).

**Four classes are set aside** for the person (pending items and `host.json` written with the old Spanish names `borrar`, `gastar` and `enviar` are still read): `delete` (what cannot be recovered: `rm -r` of anything but `node_modules`, `target`, `dist` or `/tmp/…`, backups, `find -delete`, `mkfs`, `dd of=/dev/…`, `DROP`/`TRUNCATE`, volumes, `terraform destroy`…), `spend` (cloud resources that cost money), `send` (mail, a push to a shared branch or a forced one, `gh pr merge`/`comment`/`review`, publishing a package, `curl`/`wget` sending data to a host that is not local) and `control` (Clio's own setup and folders, its services, `sudoers`, `visudo`, turning the machine off, who may use the machine: `useradd`, `usermod`, `passwd`… and `authorized_keys`, and the D-Bus clients that reach a service manager outside the launcher: `systemd-run`, `gdbus`, `dbus-send`, `busctl`). The table lives in `crates/clio-toolhost/src/ask.rs`; `host.json` can only add to it. A command is cut into simple commands (`;`, `&&`, `||`, `|`, `$(…)` outside quotes; shell keywords, wrappers like `sudo`, `env`, `xargs`, `timeout`, `nice`; the script of `bash -c`/`su -c` and what `docker exec` runs) and each is classified. **The list is a list, not a wall:** a script, a variable or an alias gets around it. What is left against that is the action log and the prompt's rule (`prompts/system/clio-host@7.md` today: do not try it another way), not this module.

**Set aside, not stopped.** The action does not run; the model gets a fixed answer that names the id and the class and tells it not to try another way (rule `host/aside`; built in `pending.rs`, `aside_text`) and goes on with the rest. The pending action is saved in `Dirs.data/host/pending/<id>.json` (0600) with a hash over the tool and its arguments; the same action again in the same session gets the same id. The person answers with `clio pending`, `clio approve ID`, `clio reject ID`, or at the end of a chat turn: `y` (or `s`) and then Enter runs it, `n` or Esc rejects it, and any other key decides nothing, since the question can open while the person is typing. The question hears its first key only after it has been on screen for a second with no key pressed. What is shown and approved is read from the saved arguments every time; an item whose stored text no longer agrees with them does not run. An approved action runs once, exactly as saved (the hash is checked), without being classified again. **A pending action expires after 24 hours**: approving it later runs nothing and says when it expired. **At most 3 questions a local day** (`questions_per_day`): past that, a pending action is born with `ask: false` and goes to the day's summary; the ones the person answered at the terminal do not count.

**Copy before change, and exact undo only for the file tools.** `fs_write` and `fs_mkdir` copy the file they replace (`runs/<id>/toolhost/backups/<n>`) and write a line in `changes.jsonl` (path, backup, mode, the hash of what was written) before they change anything. `clio undo ID` on a host session walks it back, last first: it restores content and mode, removes what was new, and leaves alone a file that changed after Clio wrote it. What a command changes has no copy and no undo; the prompt asks the model to change files with `edit`/`write`.

**The action log** (`Dirs.data/host/actions.jsonl`, 0600): a line before and a line after every `exec`, `fs_write` and `fs_mkdir`, and one for what is set aside or denied (`at_ms`, `run`, `session`, `tool`, `what` scrubbed of known keys, `network`, `outcome`, `rule`, `exit_code`). If the line before cannot be written, the action does not run. `clio actions` shows it.

**A budget per day, not per task.** In host mode `max_steps` and `max_seconds` do not cap a prompt; `limits.day_cost_micro_usd` (factory 3,000,000) and `limits.day_steps` (factory 1000) cap all sessions of one UTC day together, kept in `Dirs.data/host/day.json`. The cost cap per prompt and the anti-loop stay. When the day's budget is spent, the session says so and does nothing more until the next day.

**Factory mode (2026-11-18).** By the owner's decision, host is now the factory mode: a `config.json` without `"mode"`, and the one `clio init` writes, mean host. The reason: an agent that only sees a copy cannot manage the server it lives on, and that is what Clio is for. `"mode": "copy"` and `--copy` keep copy mode. `clio run --workspace DIR` names a folder, so it is a copy of that folder (with `--host` it is an error); without `--workspace`, `clio run` follows the configuration. The builtin loop has no host mode, so without Pi a host configuration asks for `--copy` (or `clio pi install`). The test worlds and the suites that test copy behaviour say `copy` explicitly.

## Time limits and stopping (2026-11-18)

- **The model decides a host command's time limit.** `timeout` (seconds) is an optional argument of the host `bash`, described in the guard's schema. Given, it is enforced and capped at 3600. Absent, the command has no limit: no `RuntimeMaxSec`, no kill timer, no client timer. Copy mode keeps its fixed limit.
- **A running host command stops** when its caller goes away (Esc or an abort: the guard drops the connection and the tool host sees it), when the service stops (quit, SIGHUP or SIGTERM, the end of the session: its input closes and the tool host stops what runs before it exits), under both launchers (the process group is killed; the systemd unit is stopped). The closing line in the action log then says `stopped`. Before, an abort left the command running to its 120 s.
- The Pi client's silence and run deadlines do not count while a tool runs.
- **While a command runs the tool host still answers** `filter`, `judge`, `jobs`, `job_output` and `job_stop`: they take no lock the command holds, so the guard's filter and a job stop are never stuck behind it. A request whose client left while it waited for the one before is refused (`the caller went away before the call ran`): nothing runs for nobody.

## The judge at the door and the `suspect` mark (2026-11-18)

A tool result that marks the session (copy mode: every read and command; host mode: a foreign folder, a networked command, a program that reaches out, logs) is judged when the guard filters it, before the model reads it. The judge is the one that already guards what the agent saves (S-64): the same process, the memory port, and the key bound to its destination in the vault. It runs only when Jev is on (`"jev": {"enabled": true}`), against TypeSafe's Jev or against Temis, the owner's own service, which speaks the same protocol through the same adapter. The tool host gains no new way out.

- **The question.** One closed question, `injection` (a probability), with the state `{text, source}`: the text and the path or command it came from, both cleaned by the vault first. The judge reads all of a text: in windows of 24 KiB that overlap by 2 KiB (an injection on a boundary is read whole in one of the two), all asked at once. Beyond 16 windows (about 350 KiB) the text counts as unjudged, like a judge that did not answer. The tool host answers a new op, `judge {text, source}`, so the brain can judge what an approved action printed, which runs in another process.
- **An injection** (at least 0.9, the bar that refuses an unsafe memory): the model gets a notice Clio builds, with only the size and the source; the text is kept for the person in `runs/<id>/toolhost/withheld/<ms>-<n>.txt` (mode 0600, cleaned); the session is marked `suspect` (kept in `tainted.json` and restored when the session is reopened); the action log gets a line (outcome `withheld`, rule `judge/injection`); the chat shows a quiet note with the file to read.
- **An approved action's output is judged too**, before the model sees it, through that same op; and a command that asked for no `timeout` runs, once approved, with the 3600 s limit (the question says so), since nobody in the chat can stop it.
- **No answer** (down, an error, past 5 s) or **no judge**: as before. When the judge is on and silent, the chat says so once per session.
- **A suspect session asks before it reaches out.** In a session the judge flagged, every command that asks for the network, runs a program that reaches out by itself (`docker`, `docker-compose`, `podman`, `ssh`, `scp`, `rsync`, `crontab`, `at`, `batch`, `nsenter`, `unshare`, `machinectl`, `busctl`, `dbus-send`, `ip netns exec`), or names `sudo` anywhere (root reaches past every cut of the launcher) is set aside as send, with the reason "the session read text the judge flagged" kept in the pending item and shown in `clio pending` and in the chat's question. The class of the list is checked first; this comes after it. A session that is only marked (the judge found nothing, or was silent) gets no new questions. When a session becomes suspect, its background jobs that have the network (asked for, or a program that reaches out) are stopped; the log line has the rule `judge/suspect` and `job_output` says why. Local jobs go on.

## Background commands (2026-11-18)

In host mode `bash` takes `background: true`. The command goes through the same path as one in the foreground (the list, the suspect rule, the launcher, the masks, the network rule, the action log) and the answer comes at once with a job id (`j1`, `j2`, …). Two tools exist only in host mode: `job_output` hands over what the job printed since the last read (cleaned, judged when the job reached out, at most 64 KiB a read) and, once it ended, its exit code; `job_stop` stops one.

- At most 4 jobs run at once in a session.
- `job_output` hands over whole lines only while more may come, since a value cut in two would get past the scrubber, which knows only whole values; `runs/<id>/toolhost/jobs/` is removed when the session's jobs end.
- A job's output goes to `runs/<id>/toolhost/jobs/<job>.log` (0600), capped at 4 MiB: past that the oldest half is dropped, and the next read says so.
- Every job stops when the service stops (`ToolHost::stop`): the end of the session, the person quitting, a signal.
- The action log gets a `start` line, then `done` or `stopped`.
- The chat shows how many jobs run, and a quiet note when a turn ends with jobs still running.

## Questions and secrets for the person (2026-11-18)

- **`ask_person`** asks one question with 2 to 4 answers (the first is the recommended one); the person can also type their own. In the chat it is a box the person answers; with no person (`clio run`) it answers at once that nobody is there, and the model decides and says what it assumed. Esc skips it; after ten minutes it counts as no answer. The model gets only the label picked or the words typed, cleaned.
- **`request_secret`** (name, destination as `TOOL:DOMAIN`, why) asks the person to put a secret into the vault. The tool host checks the name with the vault's rules and the destination with the vault's own parser (the tool is `[a-z_]+`; the host has at least two labels, none empty, since the vault binds a value to the host and every name under it), and asks the vault's person socket only whether it is open and which names it has: a stopped or locked vault, or a name already there, is refused at once. The request waits in `pending` as a new class, `secret`: it is never run (the tool host's `approve` refuses it), `host.json` cannot add it, it expires after 24 hours and counts against the day's questions. It works only where a person can answer (the chat, not `clio run`).
- **`memory`** (2026-11-18): a change to the person's blocks (`memory_block_edit`) from a session marked `tainted` or `suspect` waits as this class instead of being refused (design `docs/specs/2026-11-18-continuous-conversation-design.md`, section 5). The item keeps the block, the action, the text as it would be written and, for a replace or a remove, the entry as it read then. Like `secret` it is never run (the tool host's `approve` refuses it) and `host.json` cannot add it; it is bound by hash, expires after 24 hours, counts against the day's questions and is logged (`aside`, `approved`, `rejected`). It waits in a chat in copy mode too. The chat's Approval box shows it whole (scrolled, never cut; `y` arms only once its end was on screen) and `clio approve` prints the same; approved, `pending::approve_block` writes it from the person's `clio` process through the same memory port a clean session uses, with the person's origin, once, and writes nothing if the target entry changed meanwhile. The model learns the outcome with the next message.
- **`skill`** (2026-11-18, S-68): a skill draft (`skill_write`) that its review passed but cannot be registered by itself (a `passes` with no findings in a marked session, or a review that could not check) waits as this class. The item keeps the draft as stored (SKILL.md, the files, the digest of both) and why it waits. Like `memory` it is never run (the tool host's `approve` refuses it), `host.json` cannot add it, it is bound by hash, expires after 24 hours, counts against the day's questions and is logged (`aside`, `approved`, `rejected`); it waits in copy mode too. The chat's Approval box shows SKILL.md whole and each other file's name and size (scrolled, never cut; `y` arms only once its end was on screen), with the suspect line in a suspect session and the reason when the review could not check; `clio pending` lists it and `clio approve` prints the same and, approved, `pending::approve_skill` registers it from the person's `clio` process, once, byte for byte (the digest is checked again).
- **The value never passes through Pi, the guard, the tool host, the model, the logs, the pending file or the session.** At the end of the turn the chat shows a box with the name, where it may be sent, the reason, a line when the session is suspect, and a masked field. Enter stores the value with a `Put` on the vault's person socket, from the TUI process, never replacing an existing name; Esc declines. At the terminal, `clio approve <id>` on a secret request asks for the value with no echo and stores it, and `clio reject <id>` declines it. The model learns with the next message, as data, that the secret was saved (and where it is bound) or declined.
- **No tool of the model can use a stored secret yet.** The prompt says so; a secret requested today is kept for later work.

## The prompt

`prompts/system/clio-host@7.md` is the host prompt now: `@6` plus one Skills section (S-68). `@6` is `@5` (the rules of `@4` written in English, plus a line saying the model answers in the language the person writes in) with only the passage on the person's blocks changed (in a session that read outside content a block change waits for the person's approval). Over `clio-host@2` it adds: give `timeout` when a command should end by then and leave it out for long jobs; never leave a server or a watcher in the foreground; start long commands with `background: true` and check them now and then; what a withheld result means and not to read it another way; `ask_person`, `request_secret` and `todo_write` (a checklist for jobs of 3 or more steps, shown above the chat's status line).

## Known limits

- **With `sudo` the masks are not a wall.** Under `Systemd` a command can `sudo` and read or change anything, Clio's folders included. The masks keep them out of an ordinary command's sight, not out of root's reach.
- **Under `Systemd`, even without `sudo`, a command of the same user reaches Clio's files through `/proc/<clio pid>/root/…`**: the unit runs as the person, and the toolhost is a process of the person. Checked by hand on the VPS on 2026-11-17: a decoy in a masked folder was read that way. `bwrap`'s own pid namespace closes this one way (the command sees only its own processes); systemd 255 has no equivalent (`PrivatePIDs=` came later). It does not make the masks a wall under `bwrap` either: see the next point.
- **Sockets of daemons outside the jail stay reachable under both launchers.** `bwrap --bind / /` and the systemd unit both see `/var/run/docker.sock` and the person's D-Bus (`/run/user/<uid>/bus`). `--unshare-net` and `PrivateNetwork=yes` cut the network, not Unix sockets. So a command without `network: true` can use Docker, and membership of the `docker` group is root: it reaches the internet and Clio's data through a volume mount. And it can ask the person's systemd to run something outside the launcher, unmasked (`systemd-run --user …`, `gdbus`/`dbus-send`/`busctl` calling `StartTransientUnit`), `clio approve <id>` included. The sockets are not masked, because managing Docker and the person's services is legitimate work. What stands against it: `systemd-run`, `gdbus`, `dbus-send` and `busctl` are `control`; `docker`, `docker-compose`, `podman`, `ssh`, `scp` and `rsync` mark the session (`web`) without `network: true`; the log; the prompt.
- **Two host sessions at once can undercount the day's budget**: each loads `day.json`, counts on its own, and the last save wins.
- **An approved action runs in a separate process**: `clio approve` (and the chat's question) build a new host-mode toolhost on that session's run folder, with a fresh launcher self-test. It does not go through the session's own toolhost; when the chat feeds the result to the model, the brain marks the session itself.
- The `/tmp/…` exemption of `rm -r` is by the literal path: a scratch folder there is deleted without asking.
- A new host-mode session also stops the units a `clio` that died left behind (only those whose pid is dead; a pid the system gave to another process since counts as alive).
- When a host session's toolhost stops, the brain stops its leftover `Systemd` units (`sudo -n systemctl stop --no-block 'clio-host-<pid>-*'`), best effort: where there is no passwordless `sudo` that call just fails.

## Differences from the plan

- `HostCfg.launcher` is a test hook: `None` (what Clio passes) detects the launcher; tests pick `Bwrap` so they never run `sudo`.
- The doctor's host section runs only when the configuration says host mode.
- The local day of the question cap uses the system time zone (`date`), not the person's.
- `bwrap` also gets `--unshare-pid` (with `--die-with-parent`): without it a background child outlived the command.
- An item is marked `Expired` lazily, when someone tries to approve it; until then a listing and the cleanup treat one past its time as not waiting.
