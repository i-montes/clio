# adapters/pi

Pi is the agent harness of Clio (ADR 0007). This folder pins it and, in `extensions/`, holds the extension that guards it.

- `package.json` pins `@earendil-works/pi-coding-agent` to an exact version (1.4.0, MIT; it brings its own agent core and model API). `package-lock.json` is committed.
- `.npmrc` sets `ignore-scripts=true`: nothing runs at install time (S-42). Two packages in the tree declare install scripts (`@google/genai`, `protobufjs`); they never run here.
- `overrides` forces patched versions of two transitive dependencies that `npm audit` flags in 1.4.0: `undici` (high, a memory issue in an EventSource parser Clio does not use) and `minimatch` (moderate, glob matching). Remove an override when Pi ships the fix. Checked: Pi 1.4.0 runs normally with them.
- The CI installs only from the lockfile (`npm ci`), fails if it would change, and runs `npm audit`; the nightly audits again. `CODEOWNERS` makes the owner review every change here.

**How Clio launches Pi** (the Rust side does it; here for reference): `pi --mode rpc --no-builtin-tools --no-extensions -e <clio-guard> --no-mcp --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve --offline`, with `PI_CODING_AGENT_DIR`, `PI_CODING_AGENT_SESSION_DIR`, `PI_OFFLINE=1`, `PI_TELEMETRY=0` and `PI_SKIP_VERSION_CHECK=1`, and a clean environment. In copy mode the working folder is the session's copy of the project; in host mode (`CLIO_GUARD_HOST=1`, ADR 0012) it is the person's home path, which Pi sees as an empty folder. Since ADR 0009 this command runs inside a `bwrap` jail (the copy read-only, its own network namespace, only the provider reachable through a host proxy, the key in the jail's environment and not in argv); Pi does not start if the jail fails its self-test.

## The guard: `extensions/clio-guard`

It is the only extension Pi loads (`-e adapters/pi/extensions/clio-guard`). **Clio does not build the tools Pi already has**: `read`, `write`, `edit`, `bash`, `find` and `ls` are Pi's (truncation, the `edit` diff, path resolution, rendering), built with `createReadToolDefinition(cwd, { operations })` and the like and registered under the same names. Only where the primitive operation runs changes: reading a file, writing it, checking access, making a folder, listing, matching a pattern, running a command. Each one is a request to the `clio-toolhost` service (`crates/clio-toolhost`) over a Unix socket.

**The exact list of registered tools** (`TOOL_NAMES` in `index.ts`; the launcher's `GUARD_TOOLS` in `crates/clio-brain/src/pi/session.rs` must match): `read`, `write`, `edit`, `bash`, `find`, `ls`, `memory_search`, `memory_get`, `memory_timeline`, `memory_context`, `memory_save`, `memory_session_summary`, `memory_update`, `memory_consolidate`, `memory_forget`, `memory_revert`, `memory_pin`, `memory_block`, `memory_block_edit`, `ask_person`, `request_secret`, `todo_write`, `skill_write`, `skill_report` (twenty-four). In host mode four more: `job_output`, `job_stop`, `service_write` and `service_status` (`HOST_TOOL_NAMES`; `HOST_GUARD_TOOLS` on the Rust side), twenty-eight in all. **A review** (`CLIO_GUARD_REVIEW=1`, the second agent that checks a piece of work, see `docs/usage.md`) registers only `read`, `bash`, `find` and `ls` (`REVIEW_TOOL_NAMES`; `REVIEW_GUARD_TOOLS` on the Rust side), whatever the mode, so its own prompt prefix caches: in host mode its `bash` keeps `timeout` and `network` and has no `background`. Its prompt is `clio-reviewer@3` (`prompts/system/clio-reviewer@3.md`; `@1` and `@2` stay as published; `@3` defines the verdict: `fails` only for a failed check, a thing that does not do what it says or one unsafe to run unattended): run the given check (or design the smallest one), try to break the work, change nothing outside a scratch folder, and answer only with the fixed `review` block; nobody can be asked (no `CLIO_GUARD_PERSON`), and its tool host (`clio toolhost --review`) refuses what would be set aside for the person, every tool but the four, and the network and `sudo` even when `bash` asks for `network`.

**`grep` is not offered.** Pi's `grep` always starts `ripgrep` on the machine (its `operations` only cover reading the context lines), so it cannot be confined with `operations`: it could read whatever the person can read. The model uses `bash grep` or `find`. There is no `powershell`, `codemode`, `tool_search` or MCP either.

**What it does**
- Each primitive operation travels to the service, which decides (the gateway over the normalized operation), runs it, cleans the result and marks the session as tainted if the content came from outside. In copy mode it runs in the working copy (sandbox, canonical paths, links that point outside refused, `extensions`, `skills`, `.pi`, `.claude`, `.git`, `.agents`, `.vscode`, `.husky`, `.githooks`, `.cargo` and `.devcontainer` not writable), and `bash` **always** runs in the `bwrap` jail (the only free shell, S-12); if the jail does not pass its self-test, `bash` fails closed (the gateway denies it by S-02). In host mode paths go to the service absolute, and `bash` takes three more arguments: `timeout` (seconds; none means no limit), `network` (no network unless asked; asking marks the session) and `background` (start it and get a job id at once).
- `tool_call`: defense in depth with the exact list; it blocks any tool that is not one of its own and, in copy mode, `write`/`edit` outside the folder or into a protected folder; it records the block in the session (`clio-guard.block`) and on stderr.
- `tool_result`: every result, whatever format Pi gave it (truncation notices, diffs, `details`), goes through the service's `filter` operation: escape sequences sanitized, the vault's scrubber, and the outside-data wrapper. The memory tools come wrapped by the service already, and `ask_person`, `request_secret` and `todo_write` answer with the person's words or Clio's own: those are only cleaned, never wrapped. With the judge on, the service may withhold the result (the model gets a notice with its size and source); the guard records it as `clio-guard.withheld`, and a silent judge as `clio-guard.judge`, for the chat to say. If the service cannot filter, the result is withheld.
- `ask_person`: one question with 2 to 4 answers, through Pi's own dialogs (`select`, then `input` for "Other…"). Only when a person can answer (`CLIO_GUARD_PERSON=1`, the chat); otherwise it answers at once that nobody is there.
- `request_secret`: forwards name, destination and reason to the service, which checks them and stores the request. The value never comes through here.
- `todo_write`: keeps the model's checklist for the session and shows it as Pi's widget `clio-todo` (the chat draws it above the status line; `clio run` prints it).
- `skill_write` (name, description, body, verify, files, reason) and `skill_report` (name, outcome, note): forwarded to the service, which checks the draft, has the judge read it and stores it as a draft (never in the skills folder), or records the report with the session's mark (S-68). Their answers are Clio's own: only cleaned.
- `service_write` (name, description, schedule, command, verify, files, network, secrets, writes, limits, reason; host mode only) and `service_status` (name optional; host mode only), S-69: forwarded to the service. `service_write` checks the draft, has the judge read it and stores it as a draft (never in the services folder); its answer is Clio's own, only cleaned. `service_status` lists the services or one with its last runs: a run's output came from outside, so its result is wrapped and judged like `bash`'s (`PRINTED` in `index.ts`) and marks the session. No tool approves, runs, turns on or off, removes or edits a service.
- **Clio's skills** (S-68): with a chat, Pi starts with `--skill <data>/skills/live` (after `--no-skills`, so nothing else is discovered), which the jail binds read-only. `read` and `ls` on a file of a registered, enabled skill are answered by the service unwrapped and without marking (`skill: true` in the answer: the service decides it from the canonical path; the guard only relays it); the guard remembers those calls by id (`clio-guard.skill-read`, restored in `session_start`) and does not wrap their results in `tool_result` or `context`, only for `read` and `ls`, never for an empty id, and not once a new call reuses that id (forgotten at `tool_call`, recorded as revoked) or two results share it. Anything else in that folder is read like any file. The start check accepts the skill commands Pi lists only when their file is under that folder. A new skill reaches Pi at its next start: Pi's RPC has no reload, and `ctx.reload()` reloads the guard itself mid-session.
- `project_trust`: always "no". `user_bash` (the RPC client's `bash`): goes through the same path as the model's `bash`.
- `before_agent_start`: the versioned system prompt (`CLIO_GUARD_PROMPT_FILE`, `CLIO_GUARD_PROMPT_VERSION`, for example `clio-agent@23` or `clio-host@7`) plus the tool notes. `memoryLayer()` is a hook for memory and is not implemented (the brain puts memory before the person's message instead). If the file is missing or does not match, the extension does not load and **Pi refuses to start** with a clear error (tested).
- `context`: whatever does not already come with a real wrapper (coherent header, footer and hash) is wrapped as data; compaction summaries too. The person's answer to `ask_person` is theirs and is not wrapped.
- Taint (S-05): `pi.appendEntry("clio-guard.taint")`, restored in `session_start` (over every branch), sent to the service with every request. There is no way to clear it.
- `session_start` reports (`clio-guard.tools`) which tools are active and where each comes from, for the start check, with the catalog of what each tool is for.
- No network, no `eval`; it reads only the prompt file and talks only to the socket in `CLIO_TOOLHOST_SOCKET`.

**`--no-builtin-tools` stays.** Checked: with the flag and the extension, the tools with a built-in name that the extension registers stay active and the model receives exactly the guard's list; without the extension the model receives zero tools (`failclosed.rs`); and an extension that does not load stops Pi.

**What it does NOT do**
- It is not a security boundary: it runs inside Pi's process, as the person, inside Pi's jail. What protects the machine is the service, the gateway, the judge, the sandbox or the host launcher, and the jail (see `docs/threat-model.md`).
- It does not answer a gateway "ask": that is a no.
- It does not write the memory by itself or authenticate to the service beyond the socket's permissions; the service serves the memory tools.
- `edit` reads the file as it is (not cleaned) so it can write it back without damage; its result is cleaned at the end.

**Start check.** Pi's RPC has no command that lists the tools. The launcher reads the `clio-guard.tools` entry (`get_entries`) and requires that the active tools are in its allowed list (`GUARD_TOOLS`, plus `HOST_GUARD_TOOLS` in host mode) and that they come from Clio's extension; with no extension there is no entry and the allowed list requires zero tools. That is what the extension says of itself; the independent check is the `tools` list the model receives in its first request (the tests check it). Reference implementation: `crates/clio-brain/tests/pi_stack/common/mod.rs` (`Pi::verify_tools`).

**How it is tested**
- `npm run check` (tsc without emitting, TypeScript 5.9.3 pinned exactly) and `npm ci --ignore-scripts && npm audit --audit-level=high`.
- `cargo test -p clio-toolhost`: the service alone. `cargo test -p clio-brain --test pi_stack`: the REAL Pi with a fake model, launched by `pi::launch::build` (the same jail `clio` uses): `stack.rs` (attacks 38 to 49), `failclosed.rs`, `latency.rs`. They need `node` and `npm ci` done; without them each test says `SKIPPED`, and with `CLIO_REQUIRE_PI=1` they fail. `bash` and Pi's jail need `bwrap` (`CLIO_REQUIRE_JAIL=1`).

**Updating Pi (task 102):** change the exact version, run `npm install --package-lock-only --ignore-scripts`, read the diff of the lockfile and the release notes, rerun `npm audit`, run the bench and the attack battery, and only then merge. Never `^` or `latest`.

**The Rust side** is `crates/clio-brain/src/pi/`: `install` embeds this `package.json` and `package-lock.json` (so the installed binary needs no repository) and runs `npm ci --ignore-scripts` into `~/.local/share/clio/pi/<version>/` (`clio init`, `clio pi install`, `just install`); `launch` starts Pi with exactly the flags and environment above and fails closed; `rpc` is the JSONL client; `sessions` lists Pi's session files. Tests: `crates/clio-brain/tests/pi_*.rs` run the real Pi from this folder's `node_modules` against `testing/fake-provider/` (skipped with a message without it; `CLIO_REQUIRE_PI=1` makes the skip a failure). Changing the pinned version here changes what `clio` installs the next time it is built.
